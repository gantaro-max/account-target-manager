# account-target-manager

**Google Apps Script + スプレッドシートで構築した、階層型のBtoB営業ターゲット管理ツール（SFA/CRM）**

「取引先 → 部署 → 案件 → 活動ログ」の4階層で営業活動を管理し、
ロール別の権限制御・月次レビュー・統計可視化・CSV出力までを1つのWebアプリにまとめています。

インフラを持たず、Googleアカウントだけで動くことを制約条件として設計しました。

---

## 特徴

### インフラゼロで動く

サーバーもDBも不要です。スプレッドシートをDBとして扱い、GASのWebアプリとして公開します。
運用コストはGoogleアカウントの範囲内で完結します。

### GASの実行時間制限を前提にした同期設計

GASには1実行あたり6分の制限があり、`google.script.run` の往復も安くありません。
そのため**フロントエンドのメモリ上で編集を積み上げ、最後に一括Upsertで同期する**方式を採っています。
操作のたびにサーバーへ書きに行く設計では、実用的な速度になりませんでした。

### 階層データの整合性をアプリ側で担保

スプレッドシートには外部キー制約もカスケード削除もありません。
そのため以下をアプリケーション層の不変条件として実装しています。

- **ID採番規則**: 取引先 `a`／部署 `d`／案件 `p`／ログ `l` + timestamp
- **カスケード削除**: 取引先を消せば、配下の部署・案件・活動ログ・ステージ履歴まで連鎖削除
- **ステージ変更履歴**: 案件の進捗ステージが変わるたびに `stage_history` へ追記

### 4段階のロールベースアクセス制御

| ロール | 権限 |
| :--- | :--- |
| `admin` | 全権限。全ユーザーのデータ閲覧・編集、取引先削除、設問管理 |
| `manager` | 全取引先の閲覧（読み取り専用）。設問管理・月次評価コメントの編集 |
| `leader` | 担当取引先の閲覧・編集 |
| `member` | 担当取引先の閲覧・編集のみ |

権限はUIの出し分けだけでなく、**GAS側でも `_requireManager()` 等により二重に防御**しています。
フロントエンドを迂回して関数を直接呼んでも通りません。

## 主な機能

| 機能 | 概要 |
| :--- | :--- |
| ターゲット管理 | 取引先・部署・案件の階層CRUD。マスターからの検索補完、重複登録の防止 |
| 案件ステージ管理 | 0（未接触）〜4（クロージング）の5段階。期限超過の視覚的アラート |
| 活動ログ | 訪問日・同行者・内容の記録。Googleドライブへのファイル添付 |
| クイック登録 | 取引先 → 部署 → 案件を1フローで連続登録するウィザード |
| 月次レビュー | KPI自動集計（接点部署数・同行回数・提案中案件数）とセルフチェック |
| 統計 | Chart.js によるステージ別・受注失注・月別活動・担当者別のグラフ |
| キャンペーン | 期間限定の重点取組を案件に紐付け。期間内のもののみ選択肢に表示 |
| CSV出力 | 取引先・案件・期間の3フィルターを組み合わせた18列統一フォーマット |
| メールリマインダー | 時間トリガーで期限超過の案件を担当者へ自動通知 |

## 開発プロセス：指示書駆動 × 多エージェントレビュー

本プロジェクトは、**設計するAIと実装するAIを分離し、その間に指示書という書面を挟む**開発フローで構築しました。
リポジトリ内の [`CLAUDE.md`](CLAUDE.md) / [`AGENTS.md`](AGENTS.md) が、実際に使用したエージェント定義です。

### なぜ書面を挟むのか

設計と実装を同じAIが続けて行うと、実装中の判断が設計の一部なのか妥協なのかを後から区別できません。
仕様が会話ログの中にしか存在しないため、**実装が仕様通りかを検証する基準そのものが失われます。**

そこで仕様を確定させる工程と、それをコードにする工程の間に `plan_*.md` を挟みます。
実装の正しさが「動くかどうか」ではなく「**書面と一致するかどうか**」で判定できるようになります。

指示書の粒度は、関数名・配置場所・定数・列順・ファイル名形式まで書き下します。

> 「よしなに」「適切に」という言葉が残っていたら、まだ設計が終わっていない。

### 4観点 × 2ステージのレビュー

指示書で確認できるのは「実装が仕様通りか」だけです。
**指示書に書かれていない「安全性」と「整合性」は、専用の視点を立てないと誰も見ていない状態**になります。
この2つを分解したものが Agent-A〜D です。

| 関心事 | エージェント | 「何と」照合するか |
| :--- | :--- | :--- |
| 安全性 | **Agent-D** | 汎用的な脆弱性パターン + GASの制限 |
| 整合性 | **Agent-A** | 指示書（`plan_*.md`）※スコープ外変更の検出を含む |
| 整合性 | **Agent-B** | データ構造（[DATABASE_DESIGN.md](docs/DATABASE_DESIGN.md)） |
| 整合性 | **Agent-C** | 画面フローと実装パターン（[UI_FLOW.md](docs/UI_FLOW.md) + [PATTERNS.md](docs/PATTERNS.md)） |

整合性が3つに分かれているのは、**照合先のドキュメントが3つあるから**です。
観点を先に決めたのではなく、**SSOT の数だけレビュー担当を立てる**という考え方をしています。

この構造には副作用があります。**ドキュメントに書かれていない不変条件は、担当エージェントが存在しないため検証されません。**
これは欠陥ではなく、SSOT を書き足す動機づけとして機能します。

### 「一貫性」を検証可能にする

レビュー観点で最も曖昧なのが「既存コードと一貫しているか」です。
[`docs/PATTERNS.md`](docs/PATTERNS.md) で **「同じことをする方法は1つに固定し、表で明示する」** ことで、
主観的な観点をチェックリストで機械的に検証できる観点に変えています。

| 用途 | 正解パターン |
| :--- | :--- |
| 通常のGAS呼び出し | `showOverlay("...")` → 完了後 `hideOverlay()` |
| CSVダウンロード系 | `Swal.showLoading()` → 完了後 `Swal.close()` |
