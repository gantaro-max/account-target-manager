## A. セキュリティ修正（最優先）

### A-1. `renderTimelineLogs()` 格納型 XSS ★CRITICAL★

**対象ファイル**: `src/js_log.html`  
**該当箇所**: `renderTimelineLogs()` 関数内の `innerHTML` 展開（約 line 285 付近）

**問題**: `l.content`・`l.accompaniedBy`・`p.name`・`p.targetProduct`・`dName` がエスケープなしで  
テンプレートリテラルの `innerHTML` に展開されている。スプレッドシートにスクリプトを含む文字列が  
保存されると全ユーザーの画面で実行される（格納型 XSS）。

**修正要件**:
1. `renderTimelineLogs()` 内で `innerHTML` に渡すテンプレートリテラルの**すべてのユーザー由来フィールド**に  
   `_escapeHtml()` を適用する（`js_core.html` に定義済みの共通関数を使用）。
2. 対象フィールドの列挙（漏れなく適用すること）:
   - `l.content`
   - `l.accompaniedBy`
   - `p.name`（案件名）
   - `p.targetProduct`（対象製品）
   - `dName`（部署名）
   - その他テンプレート内のユーザー入力由来の変数すべて

**完了条件**:
- `renderTimelineLogs()` の `innerHTML` テンプレート内でユーザー由来フィールドが全て `_escapeHtml()` でラップされている。
- `l.id` や `p.id` などの ID 値もエスケープ対象に含まれていること（後述 A-3 参照）。

### A-2. `showAlert` / `showConfirm` の html: フィールドに生文字列を渡している

**対象ファイル**: `src/js_core.html`  
**該当箇所**: `showAlert()`・`showConfirm()` の `Swal.fire({ html: message })` 呼び出し部分

**問題**: SweetAlert2 の `html:` フィールドは HTML として描画される。現状 `message` をそのまま渡しているため、  
呼び出し元が未エスケープのユーザー入力を渡すと XSS が成立する。  
実際に `js_account.html` の `_checkDuplicateAccount()` が取引先名をエスケープなしで渡している例が確認されている。

**修正要件**:

関数側でエスケープする（全呼び出し元を一括保護）:
```js
// showAlert / showConfirm の html: に渡す前に自動エスケープ
html: _escapeHtml(message)
```
HTML タグを意図的に含むメッセージが将来必要になった場合は `showAlertHtml(rawHtml)` を別関数として追加する。  
現時点では全 `showAlert` / `showConfirm` 呼び出しはプレーンテキストのみを渡しているため、エスケープして問題ない。

**完了条件**:
- `showAlert` / `showConfirm` にユーザー入力文字列が渡されても XSS が成立しない状態になっている。

### A-4. `estimateUrl` の `javascript:` スキーム XSS

**対象ファイル**: `src/js_log.html`  
**該当箇所**: `editLog()` または `renderTimelineLogs()` 内の `<a href="${log.estimateUrl}">` 生成部分（約 line 39 付近）

**問題**: `estimateUrl` をエスケープなしで `href` 属性に埋め込んでいる。  
`javascript:alert(1)` を含む値が保存されるとリンククリック時に実行される。

**修正要件**:
URL のスキームを検証してから出力する:
```js
function _safeUrl(url) {
  if (!url) return "";
  const s = String(url).trim().toLowerCase();
  if (s.startsWith("javascript:") || s.startsWith("data:")) return "";
  return url;
}
```
`href="${_safeUrl(log.estimateUrl)}"` として使用する。  
`_safeUrl` は `js_core.html` の共通ユーティリティに追加してもよい。

**完了条件**: `estimateUrl` を含む `href` 出力で `javascript:` スキームが無効化されている。

## B. バグ修正

### B-1. `handleLogProjChange` — 「新規案件」選択時にフォームが即座にクリアされる ★CRITICAL★

**対象ファイル**: `src/js_project.html`  
**該当箇所**: `handleLogProjChange()` 内の `"new"` 分岐（約 line 135〜146）

**問題**: 現状の実装:
```js
if (val === "new") {
  window._logProjSelectPrev = window._logProjSelectLast || "";
  openQuickAddModal("project");
  $("log-proj-select").value = "";
  loadProjectDataToForm();  // ← BUG: モーダル表示前にフォームを全消去
}
```
`loadProjectDataToForm()` が `select.value = ""` の直後に同期実行されるため、  
フォームの stage / note / next_action 等のフィールドがモーダルが開く前に消える。  
ユーザーが入力途中のデータを失う。

**修正要件**:
「新規案件」選択時は `loadProjectDataToForm()` を呼ばない。  
フォームのクリアはモーダルが閉じた後（`closeQuickAddModal` 内）に任せる。
```js
if (val === "new") {
  window._logProjSelectPrev = window._logProjSelectLast || "";
  openQuickAddModal("project");
  $("log-proj-select").value = "";
  // loadProjectDataToForm() を削除 ← ここが修正点
}
```
モーダルを閉じたとき（キャンセル）は `closeQuickAddModal()` の既存実装で復元済み。  
モーダルで新規登録成功した場合は、`closeQuickAddModal(true)` 後に select に新 ID をセットして  
`loadProjectDataToForm()` を呼ぶ既存実装で問題ない。

**完了条件**: 活動ログフォームで「新規案件追加」を選択してもフォームフィールドがクリアされない。

### B-2. `_logProjSelectPrev` の undefined フォールバック問題

**対象ファイル**: `src/js_project.html`  
**該当箇所**: `handleLogProjChange()` 内 `window._logProjSelectPrev = window._logProjSelectLast || "";`

**問題**: `_logProjSelectLast` が `undefined`（初回状態）の場合に `"" || ""` = `""` になり、  
`undefined` チェックをすり抜けて、キャンセル時に強制的に空選択に戻る。

**修正要件**:
```js
// Before
window._logProjSelectPrev = window._logProjSelectLast || "";

// After: undefined と "" を明示的に区別
window._logProjSelectPrev = (window._logProjSelectLast !== undefined)
  ? window._logProjSelectLast
  : null;
```
`closeQuickAddModal` 側の guard も `!== undefined` → `!== null && !== undefined`（または `!= null`）に合わせる:
```js
if (!skipProjectRestore && window._logProjSelectPrev != null) {
  // ...
}
```

**完了条件**: ログフォームを一度も操作していない状態で「新規案件」→キャンセルしても、  
select が不正な空選択に戻らない。

// targetUserId が指定されている場合、userCounts も projects（フィルタ済み）で集計
const baseProjects = (filterEmail !== null) ? projects : allProjects;

**完了条件**: 管理者が特定担当者を選んで統計を見たとき、全グラフが同じ案件セットを集計している。

### C-2. `getProjectReport()` — 担当者スコープフィルタなし

**対象ファイル**: `src/コード.js`  
**該当箇所**: `getProjectReport()` 関数（約 line 1016〜1137）

**問題**: `_requireManager()` で manager 以上のみ呼べるが、`getCsvData` や `getStatistics` が持つ  
担当者スコープフィルタがなく、全組織・全担当者の取引先・案件・ログを返す。  
自分の担当範囲外のデータを manager 権限で取得できる。

**修正要件（スコープフィルタ追加を採用）**:

`getCsvData` / `getStatistics` と同じ `isAll` パターンを適用する:
```js
function getProjectReport(nameQuery) {
  const user = _requireManager();          // admin / manager のみ通過
  const email = user.getEmail();
  const role = _getUserRole(email);
  const isAll = (role === ROLE.ADMIN);     // admin → 全件、manager → 自分のみ
  const filterEmail = isAll ? null : email;

  // 取引先取得: getCsvData と同じ isAll フィルタを適用
  const accounts = _getRows(SHEET.ACCOUNTS).filter(h =>
    filterEmail === null || h.assignedTo === filterEmail
  );
  const accountIds = new Set(accounts.map(h => h.id));

  // 案件取得: 取引先 ID セットで絞り込み
  const projects = _getRows(SHEET.PROJECTS).filter(p =>
    accountIds.has(p.accountId)
  );
  const projectIds = new Set(projects.map(p => p.id));

  // ログ取得: 案件 ID セットで絞り込み
  const logs = _getRows(SHEET.ACTIVITY_LOGS).filter(l =>
    projectIds.has(l.projectId)
  );

  // nameQuery フィルタ（既存ロジックをここで適用）
  // ... 以降は既存の CSV 生成ロジックを流用
}
```

- `ROLE.ADMIN` 定数は既存コードで定義済みのものを使用する。
- 既存の nameQuery フィルタロジックはそのまま残し、上記スコープフィルタと AND 条件として組み合わせる。
- admin が全件を見たい場合もこの関数を使うため、`_requireManager()` は変更しない。

**完了条件**:
- manager ユーザーが `getProjectReport` を呼んだとき、自分の担当取引先・案件・ログのみ CSV に含まれる。
- admin ユーザーが呼んだとき、全件が含まれる（従来通り）。

### D-2. 案件進捗レポートカードを統計タブへ移動し manager に開放

**対象ファイル**: `src/index.html`

**背景**: C-2 でスコープフィルタを追加したことで、manager ユーザーが自分の担当データを  
CSV ダウンロードできるようになる。これに合わせて UI 側でも manager がアクセスできるよう変更する。

**問題**:
1. 現在カードは `id="tab5"`（設問管理タブ）の中にあり、タブボタンが `admin-only` のため manager には非表示。
2. カード自体にロール制限クラスがなく、`switchTab(5)` を実行すると一般ユーザーにも表示される。

**修正要件**:

**手順 1**: 案件進捗レポートカード（`<div class="card">` の CSV ダウンロードブロック全体）を  
設問管理タブ（`id="tab5"`）から **統計タブ（`id="tab3"`）の末尾** に移動する。  
統計タブは manager も閲覧できるため、自然な配置になる。

**手順 2**: 移動後のカードに `admin-only` クラスを追加し、一般ユーザーには非表示にする:
```html
<!-- 統計タブ(tab3) 末尾に追加 -->
<div class="card admin-only">
  <!-- 案件進捗レポート CSV ダウンロードの内容（tab5 から移動） -->
</div>
```

`admin-only` クラスは `js.html` の `initApp()` にて  
`if (role === "admin" || role === "manager")` 条件で `display:""` にセットされる実装になっており、  
admin と manager の両方に表示され staff には非表示になる。意図した挙動と一致するためこのクラスを使う。

**完了条件**:
- 統計タブに案件進捗レポートカードが表示されている。
- admin / manager ユーザーにはカードが表示され、CSV ダウンロードが動作する。
- 一般ユーザー（staff）にはカードが表示されない。
- 設問管理タブ（tab5）からカードが削除されている。

## E. コード品質（余裕があれば対応）

### E-1. `_syncCalendarEvent()` のデッドコードと停止理由のドキュメント化

**対象ファイル**: `src/コード.js`、`docs/TASKS.md`  
**該当箇所**: `_syncCalendarEvent()` 関数内（約 line 548）

**停止している理由**:  
GAS のスクリプト実行はサービスアカウント（スクリプトオーナー）として動作するため、  
`CalendarApp.createEvent()` で作成されるイベントはオーナーのカレンダーに集約されてしまう。  
複数の担当者（leader・member 等）がそれぞれ自分のカレンダーで確認できることが要件であり、  
現行アーキテクチャでは要件を満たせないため意図的に無効化している。  
（OAuth ユーザートークンを個人ごとに取得・保持する仕組みが別途必要）

**修正要件**:

1. `return existingEventId || "";` の直前にコメントを追加する:
```js
// カレンダー連携は現在無効。理由: GAS はスクリプトオーナーの CalendarApp を使うため、
// 全イベントがオーナーカレンダーに集約され各担当者が自身のカレンダーで確認できない。
// 再有効化には担当者ごとの OAuth トークン取得・管理の仕組みが必要。
return existingEventId || "";
```

2. `docs/TASKS.md` の Googleカレンダー連携タスク（`[x]`）を `[ ]` に戻し、以下を追記する:
```
- [ ] **Googleカレンダー連携（設計見直し必要）**
  - ⚠️ 現在無効化中。GAS のサービスアカウント制約により、イベントが全員同一カレンダーに
    集約される問題があり要件を満たさない。担当者ごとに自分のGoogleカレンダーへ登録するには
    個人 OAuth トークンの取得・管理が必要。実装方針が固まるまで dead code として保留。
```

**完了条件**:
- `_syncCalendarEvent()` の `return` 文に停止理由がコメントで明記されている。
- `TASKS.md` のカレンダー連携タスクが「設計見直し必要」として未完了に戻されている。
