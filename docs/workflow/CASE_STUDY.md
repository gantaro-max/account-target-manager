# ケーススタディ：本プロジェクトでの適用結果

本リポジトリのアプリケーションは、ここで説明するワークフローを使って開発しました。
`docs/archive/` にある35本の指示書が、その実際の記録です。

## 対象

| 項目 | 内容 |
| :--- | :--- |
| 対象 | 本リポジトリの `src/`（階層型BtoB営業ターゲット管理ツール） |
| 技術スタック | Google Apps Script + スプレッドシート + Google ドライブ |
| フロントエンド | Vanilla JS / HTML / CSS（ビルドツールなし） |
| 規模 | 約 7,400 行 / 13 ファイル |
| 権限体系 | 4段階のロールベースアクセス制御 |
| 開発期間 | 約 2 ヶ月 |
| 指示書 | 35 本（`docs/archive/plan_*.md`） |
| 使用ツール | 設計・レビュー: Claude / 実装: Codex |

## プロセスの変遷

本フレームワークは最初から完成形だったわけではなく、開発期間中に段階的に組み上がりました。

| 時期 | 追加した仕組み | この体制で作られた機能 |
| :--- | :--- | :--- |
| 開発当初 | 設計AIと実装AIの役割分離 / 指示書駆動 / SSOTドキュメント体系 | 32 |
| 開発7週目 | Agent-A〜D の観点別並列レビュー / 2ステージ制 / 指示書の5セクション固定 | 3 |
| 開発7週目 | `PATTERNS.md`（実装パターン早見表） | 3 |

AIに役割を持たせて分担させるという発想自体は、公開されている事例を参考に**開発当初から**取り入れていました。
一方、**レビューを観点別エージェントに分割して並列実行する体制は、開発終盤に導入したもの**です。

### なぜ後からレビュー体制を足したのか

動機は **「安全性と整合性を、複数の視点で見る必要があるのではないか」** という判断でした。

役割分担と指示書駆動によって「実装が仕様通りか」は書面で確認できるようになりますが、
それは**指示書に書かれた範囲の話**です。指示書に書かれていない次の2つは、
別の視点を立てないと誰も見ていない状態になります。

- **安全性**: 脆弱性、実行環境の制限に触れる実装
- **整合性**: 既存のデータ構造・画面フロー・実装パターンとの噛み合い

Agent-A〜D の構成は、この2つを分解した結果です。

| 関心事 | 担当 | 「何と」照合するか |
| :--- | :--- | :--- |
| 安全性 | Agent-D | 汎用的な脆弱性パターン・実行環境の制限 |
| 整合性 | Agent-A | 指示書（`plan_*.md`） |
| 整合性 | Agent-B | データ構造（`ARCHITECTURE.md`） |
| 整合性 | Agent-C | 画面フローと実装パターン（`UI_FLOW.md` / `PATTERNS.md`） |

整合性が3つに分かれているのは、**照合先のドキュメントが3つあるから**です。
観点を先に決めたのではなく、SSOT の数だけレビュー担当を立てた、という順序になっています。

## 検証状況

どこまで実績があるかを明示しておきます。

| 要素 | 適用実績 |
| :--- | :--- |
| 指示書駆動（設計AI / 実装AI の分離） | 35機能・約2ヶ月 |
| SSOTドキュメント体系（実装先行・追従更新） | 同上 |
| 4エージェント並列 × 2ステージレビュー | 3機能（導入直後） |
| `PATTERNS.md` による実装パターンの固定 | 3機能（導入直後） |

**フレームワークの前半（指示書駆動）には運用実績があり、後半（レビュー体制）は導入直後の段階です。**
後者について、多数の機能・長期間での効果検証はまだ行えていません。
本ドキュメントは「検証済みの手法」の紹介ではなく、**実プロジェクトで組み上げた設計とその途中経過**の記録です。

## 実行環境としての制約

このプロジェクトを選んだことが、結果的にフレームワークの設計を規定しました。

- **実行時間の上限**（1実行あたり6分）→ 「都度通信ではなく一括同期」という不変条件が生まれた
- **ビルド・型検査・自動テストが実質使えない** → 品質保証を**レビュー体制側に寄せる**必要があった

2点目が効いています。テストで担保できない以上、
**コミット前にドキュメント整合で検出する**設計にせざるを得ませんでした。
自動テストが潤沢な環境なら、ここまでレビュー体制を重くする必要はなかったはずです。

## 設計上の判断とその理由

### 品質保証の重心をテストからレビューへ寄せた

ビルド・型検査・自動テストが実質使えない条件下では、「動かして確かめる」に頼りきれません。
そのため、**コミット前にドキュメント整合で検出する**設計を選びました。

### レビューエージェントごとに参照ドキュメントを分けた

Agent-B は `ARCHITECTURE.md`、Agent-C は `UI_FLOW.md` + `PATTERNS.md` と、
**観点だけでなく参照元自体を分離**しています。

同じ資料を渡して観点だけ変えると、指摘が重複しやすくなるためです。
参照元を分けることで検出対象が分散し、副次的に
**「ドキュメントに書いていない不変条件は検証されない」**という因果が生まれ、
SSOT を書き足す動機づけとして働きます。

### 判定を多数決ではなく AND 条件にした

4エージェント中3つがOKなら通す、という運用を許すと、観点を分けた意味が失われます。
1つでもNGなら差し戻す前提で、各エージェントのチェック項目を
「読めば誰でも同じ判定になる」粒度まで具体化しています。

### 指示書の粒度を「よしなに」が残らないところまで下げた

関数名・配置場所・定数・列順・ファイル名形式まで書き下します。
指示書を書く側には面倒ですが、その面倒を実装工程に先送りすると、
実装AIがその場で判断し、**レビュー時に「どちらが正しいか」を決める材料が存在しない**状態になります。

## うまくいかなかったこと・限界

### 小さな変更にはオーバーヘッドが大きすぎる

typo 修正やラベル変更にまで指示書を書くのは過剰です。

`CLAUDE.md` の**トリアージ基準**（直接変更してよいケース / 指示書を作るケース）は、
指示書運用を32本続けた後、レビュー体制と同じタイミングで明文化されたものです。
**フレームワークを常時フル適用する前提にはできません。**

### ドキュメントの陳腐化は自動では防げない

「実装先行・ドキュメント追従更新」を採用していますが、
更新を怠るとレビューエージェントが古い基準で判定します。
完了処理（TASKS更新 → archive移動 → SSOT更新）を**承認フローの一部として固定**することで
運用していますが、仕組みで強制されているわけではありません。

### レビュー体制の効果はまだ実証できていない

観点別の並列レビューを導入したのは開発終盤で、その下で作られた機能は3本です。
「重複しない指摘が出る」「差し戻しが減る」といった効果は**設計上の意図であって、
多数の機能で計測した結果ではありません。**
本ドキュメントでそれらを成果として書いていないのはそのためです。

### 実行環境の制約に起因する仕様変更は事前に潰しきれない

設計段階で実装可能性を評価していても、実行環境固有の挙動により
実装後に機能を無効化する判断が必要になったケースがありました。
（実装自体は完了しており、制約が解消すれば有効化できる形で残しています）

要件定義の完了条件に「技術的リスクを共有済み」を含めているのは、
**リスクをゼロにできないことを前提に、共有だけは必ずする**という割り切りです。

## この事例から言えること

自動テストが十分に書ける環境なら、ここまでのレビュー体制は不要です。
本フレームワークが効くのは、**テストで担保しにくい領域を多く含むプロジェクト**です。

- ビルド・型検査・自動テストが使いにくい実行環境
- UI の一貫性・権限による表示制御など、テストコストが見合わない検証対象
- 本番データが業務そのもので、試行錯誤の余地が小さい

こうした条件下では、**品質保証の重心をテストからドキュメント整合レビューへ移す**ことに
合理性があります。本フレームワークはその具体的な実装のひとつです。
