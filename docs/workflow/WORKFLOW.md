# ワークフロー詳細

## 全体像

```
要件定義 ─── 基本設計 ─── 詳細設計 ─── 実装 ─── 一次レビュー ─── 最終レビュー ─── 完了処理
   │             │           │           │           │              │              │
 設計AI        設計AI      設計AI      実装AI      実装AI          設計AI         設計AI
（壁打ち）   （骨格）   （plan_*.md）  （src/）  （A〜D並列）    （A〜D並列）  （docs更新）
```

---

## 1. なぜ設計AIと実装AIを分けるのか

1つのAIに「設計から実装まで」を任せると、次の問題が起きます。

- **設計の妥協が観測できない**: 実装中に「この仕様は面倒だから簡略化しよう」という判断が起きても、
  設計も同じAIがしているため、それが妥協なのか正しい設計変更なのか区別がつきません。
- **レビューが成立しない**: 自分が決めた仕様に対して自分が「仕様通りです」と答えるのは検証ではありません。

そこで **仕様を確定させる工程と、それをコードにする工程の間に、書面（`plan_*.md`）を挟みます。**
書面があることで、実装の正しさが「動くかどうか」ではなく「書面と一致するかどうか」で判定できるようになります。

### 実装AIに課す制約

| 項目 | ルール |
| :--- | :--- |
| 作業領域 | `src/` 配下のコードのみ |
| 仕様判断 | **しない**。疑問が出たら実装を止めて設計AIに確認する |
| ドキュメント更新 | **しない**（設計AIの担当） |
| 指示書にない実装 | **しない**。「ついでの改善」も禁止 |

最後の項目は Agent-A が明示的に検証します。良かれと思った改変が最も差分を汚すためです。

## 2. 指示書（plan_*.md）の粒度

指示書は5セクション固定です。

| セクション | 目的 |
| :--- | :--- |
| 1. 背景・目的 | 実装AIが「似た既存機能を誤って改変する」のを防ぐ |
| 2. 変更対象ファイル ＋ 機能要件 | 関数名・配置場所・引数・定数・列順まで確定させる |
| 3. UIフロー | 操作シーケンスを時系列で確定させる |
| 4. 完了条件（DoD） | **レビューエージェントがそのまま検証に使う** |
| 5. 注意事項・禁止事項 | 実装AIが気を利かせて追加しがちなものを先に潰す |

### 粒度の判定基準

> **「よしなに」「適切に」という言葉が残っていたら、まだ設計が終わっていない。**

指示書を書く側にとっては、関数名や列順まで書き下すのは面倒に感じます。
しかしその面倒を実装工程に先送りすると、実装AIがその場で判断し、
**レビュー時に「どちらが正しいのか」を決める材料が存在しない**状態になります。

### DoD の書き方

「動くこと」ではなく「観測できること」を書きます。

| ❌ 悪い例 | ✅ 良い例 |
| :--- | :--- |
| CSV出力が正しく動く | CSV の列が左から「担当者名,コード,名称,優先度」の順になっている |
| 権限制御が効いている | `staff` が該当関数を直接呼び出してもエラーが返る |
| 表示が崩れない | 優先度の左ボーダー色が `high=赤 / mid=アンバー / low=グレー` になっている |

## 3. 2ステージ・4エージェントレビュー

### なぜ4つに分けるのか

出発点は **「安全性と整合性を、複数の視点で見る必要があるのではないか」** という問題意識です。

指示書駆動によって「実装が仕様通りか」は書面で確認できますが、
それは**指示書に書かれた範囲の話**にすぎません。
指示書に書かれていない以下の2つは、専用の視点を立てないと誰も見ていない状態になります。

- **安全性**: 脆弱性、実行環境の制限に触れる実装
- **整合性**: 既存のデータ構造・画面フロー・実装パターンとの噛み合い

この2つを分解すると、4エージェントになります。

| 関心事 | エージェント | 「何と」照合するか |
| :--- | :--- | :--- |
| 安全性 | **Agent-D** | 汎用的な脆弱性パターン + 実行環境の制限 |
| 整合性 | **Agent-A** | 指示書（`plan_*.md`） |
| 整合性 | **Agent-B** | データ構造（`ARCHITECTURE.md`） |
| 整合性 | **Agent-C** | 画面フローと実装パターン（`UI_FLOW.md` + `PATTERNS.md`） |

整合性が3つに分かれているのは、**照合先のドキュメントが3つあるから**です。
観点を先に決めたわけではなく、**SSOT の数だけレビュー担当を立てる**という考え方をしています。

この順序には副作用があります。
**ドキュメントに書かれていない不変条件は、担当エージェントが存在しないため検証されません。**
これは欠陥ではなく、SSOT を書き足す動機づけとして機能します。
逆に、同じ資料を全エージェントに読ませて観点だけ変えると、この構造は成立しません。

### なぜ2回やるのか

| ステージ | 起動者 | 性質 |
| :--- | :--- | :--- |
| 一次レビュー | 実装AI自身 | 実装者による品質の作り込み。NGなら自己修正して再実行 |
| 最終レビュー | 設計AI | 実装の文脈を知らない目による検証 |

同じチェックリストでも、実装直後の自分と第三者視点とでは検出できる欠陥が異なります。
一次レビューは「明らかな抜け」を実装AI側で吸収し、設計AIに上がってくる報告の質を揃える役割です。

### 判定は AND 条件

**1エージェントでもNGなら差し戻し。** 多数決にはしません。
「4つ中3つがOKだから通す」を許すと、観点を分けた意味が失われます。

## 4. PATTERNS.md ——「一貫性」を検証可能にする

レビュー観点の中で最も曖昧なのが「既存コードと一貫しているか」です。
人間なら暗黙に共有できますが、AIエージェントには基準が必要です。

そこで **「同じことをする方法は1つに固定し、表として明示する」** 方針を取ります。

```
| 用途                          | 正解パターン                                    |
|-------------------------------|------------------------------------------------|
| 通常のバックエンド呼び出し     | showOverlay("...") → 完了後 hideOverlay()       |
| ファイルダウンロード系の呼び出し | Swal.showLoading() → 完了後 Swal.close()        |
```

これにより、主観的な「一貫性」が、チェックリストで機械的に検証できる客観的な観点に変わります。

### 運用ルール

- 新しいパターンが確立されたタイミングで**随時追記**する（最初から網羅しようとしない）
- 同じ用途に2つ目の書き方が現れたら、**どちらかを正解に決めて**表を更新し、既存コードごと寄せる
- 表にないパターンが新規に採用された場合、Agent-C は**指摘対象**とする
  （悪い実装だからではなく、「表に載せる価値があるか設計AIが判断していない」ため）

## 5. 完了処理

全エージェントがOKを出したら、設計AIが以下を実行します。

1. `docs/TASKS.md` の該当タスクを `[ ]` → `[x]` に更新
2. 使用した指示書を `docs/instructions/` → `docs/archive/` へ移動
3. 実装内容に応じて `REQUIREMENTS.md` / `UI_FLOW.md` / `ARCHITECTURE.md` を更新

### ドキュメントは実装先行・追従更新

要件定義書を先に完璧にしてから実装するのではなく、
**レビュー通過後に「実際にこうなった」を反映**します。
先に書いて実装がズレると、ドキュメントが嘘をつき始め、
SSOT を参照するレビューエージェント全体が機能しなくなるためです。

### 指示書は SSOT ではない

`docs/archive/` の指示書は「その時点の意思決定の記録」です。
仕様が変わったら SSOT ドキュメントを更新し、**過去の指示書は書き換えません。**
アーカイブは監査ログとして、なぜその実装になったかを後から追うために残します。
