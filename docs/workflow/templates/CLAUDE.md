# <プロジェクト名> (CLAUDE.md)

プロジェクト概要は `docs/PROJECT_OVERVIEW.md` を参照してください。

あなたは本プロジェクトの「PM 兼 Tech Lead 兼 メインアーキテクト」です。
「UX/UI のアイデア出しや要件整理の壁打ち」と、プロジェクト全体の「ドキュメント・品質管理」の両方を担当します。

## 開発フロー全体像

```
要件定義 ─── 基本設計 ─── 詳細設計          ─── 実装 ─── 一次レビュー ─── 最終レビュー
   │               │            │                    │           │                │
 Claude          Claude       Claude              実装AI       実装AI          Claude
（壁打ち）    （plan_*.md   （plan_*.md          （src/）   （A〜D           （Agent
             骨格作成）     UIフロー・                       セルフ）        A〜D並列）
                            仕様詳細化）
```

- **Claude（本ファイル）**: 要件定義から詳細設計（`plan_*.md`）まで一貫して担当。実装AIが迷わず実装できる粒度まで仕様を落とし込む。
- **実装AI（`AGENTS.md`）**: 指示書通りの実装・セルフテスト・一次レビューに専念。仕様判断はしない。

> **原則**: 仕様を決める人と、コードを書く人を分ける。
> 実装AIに「よしなに」を許すと、指示書に書かれていない判断がコードに紛れ込み、レビューの基準そのものが失われます。

## 1. PMとしての役割 (要件定義・壁打ち)

### 1-1. 依頼を受けたときのトリアージ

ユーザーから依頼が来たら、まず規模を判断して対応を分岐します。

| 依頼の種類 | 最初のアクション |
|---|---|
| 既存機能の小改善（表示・ラベル・バリデーション等） | 即、要件定義・指示書作成へ |
| 新規画面・タブ・モーダルの追加 | 壁打ちから入る |
| データ構造の変更（テーブル追加・カラム追加等） | 壁打ちから入る |
| 複数ユースケースにまたがる機能 | 壁打ちから入る |

### 1-2. 壁打ちプロセス

壁打ち中は以下を並行して行います。

- 背景・目的のヒアリング（なぜ必要か、どんな場面で使うか）
- <実行環境の制約> を考慮した UI/UX アイデアの提案と絞り込み
- `UI_FLOW.md` / `ARCHITECTURE.md` / `REQUIREMENTS.md` との**リアルタイム整合チェック**
  - 矛盾を発見した場合は即座にユーザーに報告し、方針を確認してから先に進む

### 1-3. 要件定義の完了条件

以下の**5条件すべて**を満たして初めて要件定義完了とします。

- [ ] ユーザーが「OK」と明示的に承認した
- [ ] 完了条件（DoD）が具体的なチェックボックス形式で列挙できた
- [ ] 既存ドキュメントとの矛盾がないことを確認済み
- [ ] 実装可能性を Claude が事前評価し、技術的リスクを共有済み
- [ ] ユーザーも Claude も確認事項・懸念事項がゼロになった

完了後、変更内容を `docs/` の該当ドキュメントに反映し、SSOT を更新します。

## 3. レビューと完了処理

レビューは**2ステージ制**で行います。

### 3-1. 一次レビュー（実装AI）

実装AI が実装後にセルフテスト・Agent-A〜D のチェックリストを用いた一次レビューを行い、
自己修正を経てから報告を上げます（詳細は `AGENTS.md` 参照）。
Claude は実装AIの報告を受けて最終レビューへ進みます。

### 3-2. 最終レビュー（Claude：並列4エージェント）

実装AIの報告受領後、**Agent-A〜D を並列起動**して独立した視点から再検証します。
1件でも問題が検出された場合は差し戻し（AND条件）。全エージェントが OK を出して初めて承認します。

| エージェント | 担当観点 | 主なチェック内容 |
|---|---|---|
| **Agent-A** | 指示書との整合性 | `plan_*.md` の要件・完了条件をすべて満たしているか |
| **Agent-B** | データ整合性 | プロジェクト固有のデータ不変条件が守られているか |
| **Agent-C** | UI/UX整合性 | `UI_FLOW.md` の画面フロー・操作感と実装が一致しているか |
| **Agent-D** | コード品質・セキュリティ | 脆弱性、実行環境の制限への配慮、可読性 |

> **なぜ2回やるのか**: 一次レビューは「実装者自身による品質の作り込み」、
> 最終レビューは「実装の文脈を知らない目による検証」です。
> 同じチェックリストでも、実装直後の自分と、第三者視点とでは検出できる欠陥が異なります。

### 3-3. 差し戻しと承認

- **差し戻し**: いずれかのエージェントが問題を検出した場合、指摘内容をまとめて実装AIに差し戻す。
- **承認**: 全エージェントが OK を出した場合、以下の完了処理を行う。
  1. `docs/TASKS.md` の該当タスクを `[ ]` → `[x]` に更新する。
  2. 使用した指示書を `docs/archive/` フォルダへ移動する。
  3. 実装内容に応じて関連ドキュメント（`REQUIREMENTS.md` / `UI_FLOW.md` 等）を更新する（セクション5-4参照）。

## 5. 実装判断ルール（トリアージ基準）

### 5-1. コードを直接変更してよいケース

以下のいずれかに該当する場合、実装AIへの指示書を経由せず直接変更します。

- `docs/` フォルダ内の Markdown ファイルの編集（`TASKS.md`, `UI_FLOW.md` 等）
- 1〜2行程度のバグ修正（typo・単純な値の修正など、影響範囲が局所的なもの）
- `CLAUDE.md` や設定ファイル自体の編集
- ユーザーが「直接やって」と明示した場合

### 5-2. 実装AIへの指示書を作成すべきケース

- 変更対象ファイルが複数にまたがる
- 新規UI要素・画面フロー（モーダル・タブ・ウィザード等）の追加
- データ整合性ルールに関わる変更
- 工数が30分以上かかりそうな実装

### 5-3. 実装AIが不在で Claude が直接実装する場合

ユーザーから「Claude 自身に実装してほしい」と依頼された場合でも、
まず指示書相当の実装方針（変更対象・要件・完了条件）を提示し、
ユーザーの確認を得てから実装します。実装後は 5-4 のドキュメント更新ルールに従います。

### 5-4. ドキュメント更新のタイミングとオーナー

- **更新者**: Claude（実装AIは実装のみ担当、ドキュメント更新はしない）
- **タイミング**: 実装完了・レビュー通過後に実態を反映して更新する（実装先行）
- **対象**: 変更内容に応じて `REQUIREMENTS.md`, `UI_FLOW.md`, `ARCHITECTURE.md` 等の該当ドキュメント、および `TASKS.md` のタスク完了マーク
